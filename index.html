O que é esse projeto e por que existe
00

Toda empresa de tecnologia que sobrevive a longo prazo tem uma coisa em comum: infraestrutura própria. Não dependência de plataformas alheias. Não forks de projetos de terceiros. Algo construído por dentro, que conhecemos cada linha, que controlamos completamente.

O SIAN é isso. É um runtime modular criado pelo Lucas — o arquiteto desta empresa — que transforma capabilities isoladas em um ecossistema coeso. Cada produto que construirmos, cada cliente que atendermos, cada ideia que explorarmos vai rodar sobre essa base.

A ideia central é simples e poderosa: capabilities são módulos independentes com contratos declarativos. O kernel descobre, valida, inicializa e orquestra. Nenhuma parte precisa saber como outra funciona por dentro. Tudo se comunica por contrato, por evento, por serviço — nunca por acoplamento direto.

E sobre tudo isso vamos construir o QG da nossa empresa: o ambiente onde trabalhamos, planejamos, atendemos clientes, guardamos decisões, lembramos onde paramos, coordenamos entre frontend, backend, vendas e marketing — em tempo real, com IA que lembra tudo.

Porta do Kernel

SIAN significa Sistema Integrado de Arquitetura de Módulos. É um kernel Node.js que roda em Termux, na porta 7700, e serve como o sistema nervoso central de todos os nossos produtos e ferramentas.

Quando o SIAN sobe, ele escaneia a pasta capabilities/, lê cada manifest.json, valida os contratos declarados, resolve dependências, inicializa cada capability na ordem correta e monta os contextos de cada projeto. Tudo automaticamente. Sem lista manual. Sem configuração central.

Regra fundamental: o Kernel não sabe o que as capabilities fazem. Ele sabe que contratos elas declaram e se a implementação cumpre esses contratos. É separação de responsabilidades no nível mais profundo.

O Studio — acessível em :7700/studio — é o painel de controle completo: capabilities, saúde, projetos, contratos, contextos, permissões, grafo de dependências, stream de eventos em tempo real. Tudo observável, tudo controlável via HTTP.

Arquitetura profunda
02

O SIAN v4 é organizado em camadas que nunca se tocam diretamente. Cada camada conhece apenas a interface da camada abaixo.

Browser / Cliente → fetch mesma origem → Servidor do Projeto
↓ proxy HTTP com X-Project-Id
Kernel HTTP :7700 → parse, auth, route → Capability API
↓ handler({ req, ctx, body })
Orchestrator + Groq → resultado → Memória Neural (disco)

O browser nunca fala diretamente com :7700. Cada projeto tem seu próprio servidor (ex: :8091 para daidoula, :8092 para asisdev) que faz proxy para o kernel. O header X-Project-Id é o que determina qual contexto, quais capabilities, quais permissões se aplicam a cada requisição.

Kernel — Composition Root
Instancia todos os subsistemas e os conecta. Não contém lógica de negócio. KernelBoot, KernelLoader, KernelRoutes, KernelHTTP, KernelGenerator — cada um responsável por uma fase. O Kernel delega, nunca executa diretamente.
ContractEngine + TypeRegistry — Validação por filesystem
O TypeRegistry descobre validadores em type-registry/*/validator.js automaticamente. Para criar um novo tipo de contrato basta criar uma pasta com um arquivo. O Kernel não sabe que WebSocket existe — sabe apenas que existe um validador para o tipo ws que implementa o hook onServerReady. Tipos ativos: api · service · ws · event · ui.
Registry + LifecycleManager — Estado das capabilities
O Registry é um Map em memória com persistência opcional via sql.js (compatível com Termux). Cada capability passa por: discovered → loaded → init → running. O LifecycleManager chama init(), start(), stop() e destroy() — todos opcionais. Se a capability não implementa, pula.
ContextManager + PermissionManager — Isolamento por projeto
Cada projeto tem um Context que contém apenas as capabilities que declarou em sian.json. O requireService() verifica permissões em dois pontos: mount e acesso. Visibility public significa acessível via API HTTP. context significa injetável apenas por outras capabilities no mesmo contexto.
EventBus + EventRouter — Comunicação desacoplada
O bus é um singleton de eventos que atravessa todo o sistema. Capabilities declaram no manifest quais eventos emitem e quais escutam. O EventRouter registra os handlers automaticamente. O Studio recebe todos os eventos via SSE em tempo real. Hot reload propaga a cascata de dependências automaticamente.

As Capabilities — o coração do sistema
03

Uma capability é a unidade fundamental do SIAN. Ela vive em capabilities/nome/, declara seus contratos em manifest.json, implementa em index.js e pode ter múltiplos contratos de tipos diferentes ao mesmo tempo. Uma capability pode ser API, serviço, WebSocket, emissora de eventos e interface visual — tudo ao mesmo tempo, se necessário.

sockets
v2.0.0
INFRA
WebSocket project-aware. Em v1 o broadcast era global — qualquer mensagem vazava para todos os clientes. A v2 resolve: cada projeto tem seu canal isolado em Map<projectId, Set<socket>>. Broadcast sem projectId gera erro explícito. O projectId vem do handshake via Sec-WebSocket-Protocol, query string ou header customizado. O WS é implementado na mão — encode/decode de frame raw sem lib externa.

O sistema de memória neural
04

O que diferencia as capabilities de IA do SIAN de um simples wrapper de LLM é a memória persistente por neurônio. Cada informação relevante sobre uma pessoa ou contexto é armazenada como um neurônio independente em disco. No próximo acesso, apenas os neurônios relevantes são ativados — scored por tags, termos, tipo e recência.

Estrutura de um neurônio
Cada neurônio é um JSON em .doulai-memoria/neuronios/neu-xxx.json. Campos: id · tipo · conteudo · resumo · tags · entidades · associacoes · confianca · origem · criadoEm · ultimaAtivacao · totalAtivacoes · status · contradizId. Gravação atômica via tmp + rename. Índice leve para retrieval rápido sem abrir todos os arquivos.

adenomiose — diagnóstico confirmado
conf: 100% · 21 ativações · origem: usuário
PREFERÊNCIA
deseja ter um filho
conf: 100% · 34 ativações · origem: usuário
FATO
25 anos de idade
conf: 100% · 17 ativações · corrigido de 19
INFERÊNCIA
interesse em tipos de parto
conf: 100% · nova ativação
FATO
acompanhamento médico há 3 anos
conf: 100% · 19 ativações
FATO
usa Alurax para controle da dor
conf: 100% · corrigido Lurax→Alurax
Detecção de contradição: quando o modelo retorna um candidato de memória que conflita com um neurônio existente (score ≥ 0.50), a contradição é detectada. Se o score ≥ 0.80, resolução automática — o novo substitui o antigo e marca o antigo como contradito. Abaixo de 0.80, fica pendente para confirmação. O sistema aprendeu sozinho que "19 anos" era errado quando o usuário corrigiu para "25 anos".

Projetos standalone — o que já existe
05

Um projeto standalone é uma aplicação independente que registra no SIAN quais capabilities precisa, recebe o sian.runtime.js e faz proxy para o kernel via HTTP. O browser nunca conhece a porta 7700. Cada projeto tem sua própria porta, sua própria UI, seu próprio domínio — mas o cérebro está no SIAN.
